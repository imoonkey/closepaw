# Phase 3 Review — Termux Bridge Manager + Bootstrap

## Verdict
REQUEST_CHANGES

## Findings

1. severity: high, file: app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:154, description: The deploy step writes the base64-encoded bridge text directly to `~/.closepaw/bridge.py`. `bridgeResourceBase64()` returns encoded bytes, but the shell command is `cat > ~/.closepaw/bridge.py`, so the deployed file is base64 ASCII rather than the Python daemon. The following `python3 ~/.closepaw/bridge.py` cannot start the bridge, and setup will fall through to `HEALTH_TIMEOUT` even on an otherwise healthy Termux install. suggested fix: Either pass the raw UTF-8 resource to `EXTRA_STDIN` and keep `cat > ~/.closepaw/bridge.py`, or keep base64 and change the Termux-side command to decode it, e.g. `base64 -d > ~/.closepaw/bridge.py`, with a marker/checksum or `python3 -m py_compile ~/.closepaw/bridge.py` before reporting deploy success.

2. severity: high, file: app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:168, description: `PORT_IN_USE` is defined but setup cannot produce it. The start command backgrounds the daemon and redirects both stdout and stderr to `/dev/null`; the bridge daemon's documented `port_in_use` stderr is therefore discarded, the shell usually exits successfully, and `waitForReadyHealth()` maps the resulting failure to `HEALTH_TIMEOUT`. This loses the specific error called out by the design and gives the user the wrong remediation path when another process owns port 18422. suggested fix: Start the daemon through a wrapper that captures startup stderr, waits briefly to see whether the process exits, and maps stderr containing `port_in_use` to `NeedsSetupReason.PORT_IN_USE`; keep other startup failures distinct from health polling timeouts.

3. severity: high, file: app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:123, description: Cancellation after `emit(SetupInProgress)` can leave the manager permanently stuck. If a setup coroutine is cancelled during a RUN_COMMAND step or health wait, no `finally`/`catch (CancellationException)` restores the previous or failed state; later `setup()` and `healthCheck()` return early whenever `_state` is still `SetupInProgress`. `startHealthPolling()` can create this path by cancelling the previous polling job while it is inside setup. suggested fix: Wrap `setupLocked()` in cancellation-safe state handling: save the prior state, restore it or emit a retryable `NeedsSetup` before rethrowing `CancellationException`, or model setup with an explicit in-flight job that future callers can await/retry instead of using the public status as the lock sentinel.

4. severity: medium, file: app/src/main/kotlin/ai/closepaw/termux/TermuxRunCommandAdapter.kt:151, description: The Android 13+ dynamic result receiver is registered with `Context.RECEIVER_EXPORTED`. The callback action and request id are random, but the receiver is only intended for the app's own PendingIntent callback and should not be exported to other apps. This violates the requested receiver flag contract and broadens the spoofing surface if the action leaks. suggested fix: Register the receiver with `Context.RECEIVER_NOT_EXPORTED` on API 33+, keeping the package-scoped mutable PendingIntent for Termux to send.

5. severity: medium, file: app/src/main/kotlin/ai/closepaw/termux/TermuxRunCommandAdapter.kt:158, description: Termux RUN_COMMAND failures returned through the PendingIntent result bundle are not classified. The adapter reads only stdout, stderr, and exitCode; Termux also reports plugin execution errors through `err`/`errmsg` in the same result bundle, including the allow-external-apps policy failure. In that path the probe simply lacks `CLOSEPAW_PROBE=ok`, so `TermuxBridgeManager` emits `NeedsSetup(UNKNOWN)` instead of `ALLOW_EXTERNAL_APPS_MISSING`. suggested fix: Parse `err` and `errmsg` from the result bundle, convert known Termux policy/setup failures to typed `RunCommandError`s, and map allow-external-apps failures to `NeedsSetupReason.ALLOW_EXTERNAL_APPS_MISSING`.

6. severity: medium, file: app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:79, description: `healthCheck()` has bootstrap side effects: any unavailable, invalid-identity, or outdated health response calls `setupLocked()`. Because `startHealthPolling()` calls `healthCheck()` every 30 seconds, passive health polling can launch RUN_COMMAND, run `pkg install`, deploy, and start Termux repeatedly instead of only updating bridge state. The design separates background health probes from user/on-demand setup and restart. suggested fix: Make health polling probe-only and emit `Ready`, `NeedsSetup(BRIDGE_OUTDATED)`, or `NeedsSetup(HEALTH_TIMEOUT/UNKNOWN)`; keep package install/deploy/start in explicit setup/restart paths, or gate auto-restart narrowly to a previously-ready bridge without rerunning package install.

7. severity: low, file: app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:29, description: The Holder path uses `context.applicationContext`, but the `TermuxBridgeManager` constructor itself is public and stores whatever `Context` the caller passes. A direct construction from an Activity would retain that Activity for the life of the manager instance. suggested fix: Normalize in the constructor (`private val context = context.applicationContext`) or make the constructor private/internal and force callers through `TermuxBridgeManager.get()`.

## Notes

- The Holder double-check locking itself is sound: the singleton field is `@Volatile`, initialized inside `synchronized`, and the Holder path passes `applicationContext`.
- `TermuxBridgeStatus` includes the full requested reason set, but `PORT_IN_USE` is currently unreachable and `Disabled` is not emitted by this phase.
- The adapter registers the receiver before `startService`, uses `FLAG_MUTABLE | FLAG_UPDATE_CURRENT`, enforces both action and requestId matching, and unregisters on result, startup failure, and coroutine cancellation.
- The health client uses explicit short OkHttp timeouts, closes responses with `use`, and parses health JSON in a way that tolerates extra fields.
- File sizes are within the 400-line limit: `TermuxBridgeManager.kt` 275 lines, `TermuxRunCommandAdapter.kt` 205 lines, `TermuxBridgeStatus.kt` 34 lines, and `AppSettingsStore.kt` 199 lines.
- I did not run Gradle verification for this review; this was a static review against the design, the two Phase 3 diffs, and the listed files.

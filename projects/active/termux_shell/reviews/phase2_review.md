# Phase 2 Review — Termux Shell Bridge Daemon

## Verdict
REQUEST_CHANGES

## Findings

1. severity: high, file: tools/termux-bridge/closepaw_bridge.py:205, description: The `/v1/exec` handler does not implement the documented request contract for `env` or `max_output_bytes`. `run_command` only reads `command`, `cwd`, and `timeout_ms`; `subprocess.Popen` inherits the daemon environment; and `Capture` always uses the module-level 256 KiB cap. Requests that set `TERM` or ask for the design's smaller 64 KiB cap silently get different behavior, and malformed `env` / `max_output_bytes` values are accepted instead of returning `invalid_request`. suggested fix: Parse and validate `env` as a string-to-string map, merge it with `os.environ`, and pass it to `Popen`; parse `max_output_bytes` as a positive bounded integer with the documented default; pass the per-request cap into each `Capture`; add real-daemon tests for env propagation, smaller output caps, and invalid field types.

2. severity: high, file: tools/termux-bridge/closepaw_bridge.py:194, description: `cwd` is not constrained to the workspace and `workspace_escape` is never returned. Any existing directory accepted by `os.path.isdir` can become the subprocess working directory, including `/tmp`, another project, or a symlink target outside `~/closepaw/workspace`. This diverges from the design's `validated_cwd` contract and documented `workspace_escape` error code. suggested fix: Resolve the workspace root and requested cwd with `Path.resolve()`, require the requested path to stay under the workspace root, return `400 {"error":"workspace_escape"}` for escapes, and cover absolute, `..`, and symlink escape cases in tests.

3. severity: medium, file: tools/termux-bridge/closepaw_bridge.py:343, description: `exec_lock` is acquired before the request body is read or validated. A slow or malformed local client can hold the single-exec lock without any subprocess running, causing valid `/v1/exec` calls to receive `409 busy` and making the busy signal reflect parser blockage rather than an active command. suggested fix: Read and validate the JSON payload before acquiring `exec_lock`; acquire the lock non-blockingly immediately before starting the command and hold it only for the subprocess lifetime; consider setting a request socket read timeout.

4. severity: medium, file: tools/termux-bridge/closepaw_bridge.py:64, description: Pidfile startup handling is not robust enough for the requested identity/dead-pid/foreign-owner lifecycle. A stale or corrupt foreign pidfile reports `port_in_use` before checking whether the pid is dead and the port is free, while a stale ClosePaw-looking pidfile with a reused live pid can SIGTERM/SIGKILL an unrelated process. suggested fix: Parse pid, port, and identity separately; if the recorded pid is dead and the target port is free, replace or quarantine the stale pidfile regardless of identity; if a live process cannot be verified as this bridge, return `port_in_use` without killing it; preferably probe the old bridge health endpoint before takeover. Add tests for stale foreign pidfiles, live old-bridge takeover, and reused/foreign live pids.

5. severity: medium, file: tools/termux-bridge/closepaw_bridge.py:382, description: All `OSError` failures while creating `BridgeServer` are reported as `port_in_use`. That conflates an actual occupied port with address-not-available, permission, bad host, and other startup failures, which misses the checklist requirement to distinguish `port_in_use` from other failures. suggested fix: Check `exc.errno == errno.EADDRINUSE` for `port_in_use`; map other startup failures to a distinct `internal_error` path with enough stderr detail for debugging; add a startup failure test that is not address-in-use.

6. severity: medium, file: tools/termux-bridge/tests/conftest.py:81, description: The host-side suite disables the watchdog for every fixture daemon and has no client-disconnect cancellation test. The current nine tests exercise real daemon happy paths for health, exec, timeout, non-zero exit, output cap, stale dead pidfile, port conflict, and busy, but they would still pass if process-group kill on client disconnect or the idle watchdog were broken. suggested fix: Add a socket-level test that starts a long `/v1/exec`, closes the client connection before the response, and asserts the child process group dies and the exec lock releases; add a watchdog test with a short configurable tick/timeout that verifies idle shutdown, pidfile cleanup, and health requests refreshing `last_request_at`.

7. severity: low, file: tools/termux-bridge/tests/test_closepaw_bridge.py:61, description: `test_exec_timeout_kills_process_group` uses `timeout_ms: 10` and then assumes the shell had time to create `child.pid`. On slower CI, the timeout can fire before `echo $! > child.pid`, producing a flaky file-read failure unrelated to daemon correctness. suggested fix: Use a less brittle timeout such as 250-500 ms, or structure the test so the child pid is confirmed before the timeout condition is allowed to fire.

8. severity: low, file: tools/termux-bridge/closepaw_bridge.py:130, description: Artifact spill naming differs from the design text. The design names `~/.closepaw/artifacts/<call_id>_stdout` and `_stderr`, while the daemon returns `<uuid>.stdout.txt` / `<uuid>.stderr.txt`. The refs are otherwise opaque, so this is mostly a contract/documentation risk, but artifact location and naming are part of the Phase 2 checklist. suggested fix: Align the filenames with the design, or update the design and tests to explicitly bless the dotted `.txt` names.

## Notes

- `python3 -m pytest tests/ -v` under `tools/termux-bridge` passed: 9 tests, 9 passed in 3.55s.
- The daemon is stdlib-only and exactly 399 lines, satisfying the Phase 2 size/style constraint.
- Health checks are unaffected by `exec_lock`, non-zero exit codes return HTTP 200, timeout responses return HTTP 200 with `timed_out: true`, and stdout/stderr drains are split across independent threads.
- Output artifact paths are generated from `uuid4().hex` plus fixed stream names, so I did not see a path traversal issue in artifact filenames.
- The design has an older line saying concurrent execs queue, but the later API contract, FAQ, and Phase 2 checklist all say immediate `409 busy`; this review treats `409 busy` as the intended contract.

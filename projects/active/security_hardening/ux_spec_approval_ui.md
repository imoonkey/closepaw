# UX Spec: Tool Approval UI

## Problem

**Who**: Users running the Android Agent in SMART approval mode (the default).

**When**: The agent wants to perform a screen-changing action (click, type, scroll, open_app) in an app the user hasn't pre-approved. The PolicyEngine classifies the app as CAUTIOUS (unknown tier) and requires explicit user approval.

**What happens now**: The capsule shows the agent "thinking," but the action silently hangs for 60 seconds, then every action card turns red with "Cancelled: Approval timed out." The user sees a wall of failures with no way to have intervened.

**Why it matters**: Without approval UI, SMART mode is unusable on any app not in the static NORMAL list. Users must either (a) pre-list every app in `app_tiers.json`, or (b) switch to AUTO_APPROVE and lose all security gates. Neither is acceptable.

**Desired outcome**: User sees a clear, fast approval prompt. They can approve once, deny, or say "always allow this app" to stop future prompts. The agent resumes within seconds instead of timing out.

---

## Flow: State Machine

```
Running
  │
  ├─ [PolicyEngine returns AskUser] ──→ WaitingForApproval
  │                                        │
  │                        ┌───────────────┼───────────────┐
  │                        │               │               │
  │                    [Approve]    [Always Allow]      [Deny]
  │                        │               │               │
  │                        │         ┌─────┴─────┐         │
  │                        │         │ persist    │         │
  │                        │         │ to runtime │         │
  │                        │         │ allow-list │         │
  │                        │         └─────┬─────┘         │
  │                        │               │               │
  │                        └───────┬───────┘               │
  │                                │                       │
  │                                ▼                       ▼
  │                        Running (action          Running (action
  │                         executes)                skipped, next turn)
  │
  ├─ [60s timeout, no response] ──→ Running (action cancelled)
  │
  └─ [Stop button] ──→ session shutdown (same as today)
```

### States

| State | Row1 (thought) | Expanded body | Row2 (buttons) | Row3 (input) |
|---|---|---|---|---|
| **WaitingForApproval** | `🛡 Approve action?` | `"{description}"\n{appName} · {reason}` | **[Allow]** **[Session]** **[Always]** **[Deny]** | hidden |

### Transitions

| From | Trigger | To | Side Effect |
|---|---|---|---|
| Running | PolicyEngine → AskUser | WaitingForApproval | emit `ApprovalRequired` event; capsule forced visible |
| WaitingForApproval | user taps **Allow** | Running | submit `Op.Approve(callId, APPROVED)` — one-time only |
| WaitingForApproval | user taps **Session** | Running | submit `Op.Approve(callId, APPROVED)` + add to session allow-list (in-memory) |
| WaitingForApproval | user taps **Always** | Running | submit `Op.Approve(callId, APPROVED)` + persist to SharedPreferences |
| WaitingForApproval | user taps **Deny** | Running | submit `Op.Approve(callId, DENIED)` |
| WaitingForApproval | 60s timeout | Running | action cancelled (existing behavior) |

### Guards
- **Always** button only shown when `packageName != null` (must know which app to persist)
- Capsule forced to CAPSULE visibility (not island) — same pattern as WaitingForInput/WaitingForAction

## Screen: WaitingForApproval

```
┌──────────────────────────────────────────┐
│ 🛡 Approve action?                       │  ← Row1: thought
├──────────────────────────────────────────┤
│ Click "Settings" button                  │  ← expandedBody: description
│ Chrome · Unknown app                     │  ← app name + reason (dimmed)
├──────────────────────────────────────────┤
│ [Allow] [Session] [Always]        [Deny] │  ← Row2: 3 allow tiers + deny
└──────────────────────────────────────────┘
```

### Button Specs

| Button | Style | Icon | Text | Behavior |
|---|---|---|---|---|
| **Allow** | FilledTonal (primary) | `✓` | `Allow` | Approve this one action only |
| **Session** | FilledTonal | `✓` | `Session` | Approve + remember for this session (in-memory) |
| **Always** | FilledTonal | `✓` | `Always` | Approve + persist to SharedPreferences (cross-session) |
| **Deny** | Outlined (error tint) | `✕` | `Deny` | Skip this action, session continues |

### Copy Rules
- **Description**: from `ApprovalDetails.description` — the human-readable action description already generated by the tool (e.g., "Click 'Settings' button", "Type 'hello' into search field", "Open app: Chrome")
- **App name**: resolve `packageName` to human-readable label via PackageManager. If unavailable, show package name
- **Reason**: from `ApprovalDetails.reason` (e.g., "Unknown app — action requires approval")

## Allow-List Persistence (Two Tiers)

### Session Allow-List
- In-memory `Set<String>` of package names
- Written when user taps **Session**
- Clears when session ends (`PolicyEngine.reset()`)
- Use case: "I trust this app for now, but don't permanently whitelist it"

### Persistent Allow-List
- Stored in `SharedPreferences` (plain, not encrypted — package names are not sensitive)
- Written when user taps **Always**
- Survives across sessions, app restarts
- Use case: "I always use this app with the agent, stop asking"
- Future: settings UI to view/revoke persistent allow entries

### PolicyEngine Check Order
```
BLOCKED?        → Deny (absolute, nothing overrides)
User allowed?   → Allow (session OR persistent list)
SMART mode?     → CAUTIOUS → AskUser, NORMAL → Allow
AUTO_APPROVE?   → Allow
ALWAYS_ASK?     → AskUser
```

### Granularity: App-Level Only (V1)
- V1: "allow" means all actions in this app are auto-approved
- No per-action granularity (e.g., "allow click but not type in Chrome")
- Natural extension for V2 but adds UI complexity without clear demand

### BLOCKED Override Protection
- BLOCKED check happens before allow-list — cannot be overridden
- The approval UI never appears for BLOCKED apps (they get Deny before reaching approval)
- Defense in depth: even if a BLOCKED package somehow enters the allow-list, it's still denied

## Edge Cases

| Case | Handling |
|---|---|
| **Rapid-fire approvals** (agent queues 3 actions) | Each shows sequentially — ToolRouter processes one at a time, next approval appears after first resolves |
| **User switches away** from capsule during approval | Capsule stays visible (forced, same as WaitingForInput). Island does NOT show approval — too small |
| **App has no human-readable name** | Fall back to package name (e.g., `com.example.app`) |
| **packageName is null** | Hide "Always" button — can't persist without knowing which app |
| **User taps Allow, then agent requests same app again** | Shows approval again (one-shot). User should tap "Always" if they want to skip future prompts |
| **Timeout while user is reading** | Cancel with existing "Approval timed out" message. Consider extending timeout to 120s since UI is now visible |
| **ALWAYS_ASK mode** | Approval UI still shown, but "Always" button hidden (user chose to always be asked) |

---

## Out of Scope (V1)

- Per-action granularity ("allow click but deny type in Chrome")
- Cross-session persistence of runtime allow-list
- Approval history / audit log UI
- Batch approval ("allow all pending actions")
- BLOCKED tier override UI
- Settings screen for managing the runtime allow-list

## Phase 6 Findings

1. severity: low, file: app/src/main/kotlin/ai/closepaw/ui/settings/AgentBehaviorSettingsPage.kt:208, description: The row renders all five status families and the `NeedsSetupReason` enum is exhaustively mapped, but several subtitles are status-only rather than actionable. `UNKNOWN` renders as "Setup error", `HEALTH_TIMEOUT` as "Bridge unreachable", and `BRIDGE_OUTDATED` as "Bridge daemon out of date"; the row also lacks the documented "tap to set up" / "tap to install" affordance. Users can tap the row, but the copy does not make the remediation obvious. fix: Add action copy either in the status subtitle or a trailing affordance, for example "Bridge unreachable - tap to retry setup", "Bridge daemon out of date - tap to update", and "Setup error - tap to retry".

No blocking Phase 6 UI issue found for the remaining checklist items: `NotInstalled`, `NeedsSetup`, `SetupInProgress`, `Ready`, and `Disabled` are rendered; F-Droid launch catches `ActivityNotFoundException`; `setup()` and `restart()` launch on `Dispatchers.IO` from a remembered scope; the toggle persists through `AppSettingsStore.termuxShellEnabled`; "Setting changes apply on the next session." is present; state uses `collectAsStateWithLifecycle`; and the Compose structure matches nearby settings rows.

## Integration Findings

1. severity: high, file: app/src/main/kotlin/ai/closepaw/session/SessionServices.kt:125, description: Fresh sessions capture `TermuxBridgeManager.snapshot(...)` from the manager's current in-memory state without triggering or awaiting a health probe. `TermuxBridgeManager` initializes `_state` to `NotInstalled` at app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:64, and `startHealthPolling()` is defined at app/src/main/kotlin/ai/closepaw/termux/TermuxBridgeManager.kt:94 but has no call sites. After an app process restart, an installed, enabled, already-running Termux bridge can still snapshot as unavailable until the user opens the settings page and its `LaunchedEffect` calls `healthCheck()`. That means `SessionToolingBootstrapper` will not register `termux_shell`, and `AgentRoleDef.resolve()` will not inject the workspace prompt for that session. This breaks the intended end-to-end pipeline and the design's background health lifecycle. fix: Start `TermuxBridgeManager` health polling from a process/service lifecycle scope, or make session creation perform a bounded probe-only health check before snapshot capture. Add a non-device test around a fresh manager/session creation path where settings are enabled and `/v1/health` is ready, asserting that the new session exposes `termux_shell` and the workspace prompt.

Other integration invariants were spot-checked as coherent: UI tools still go through `ToolName.isScreenChanging` and `PolicyEngine`; `RUN_COMMAND` is only used by the Termux bootstrap adapter; bridge and tool errors are machine-readable; `shell` and `termux_shell` have independent implementations; workspace cwd is constrained to `~/closepaw/workspace/`; v1 shell policy auto-allows; the session snapshot is immutable once captured; non-zero exit codes and command timeouts map to tool success; `termux_shell` is non-hoistable in `TurnToolPolicy`; and `/v1/exec` returns immediate 409 `busy`.

## Coverage Gaps Deferred to Human QA

- `ts-qa-workspace`: requires a physical Android device with Termux installed and configured. Human QA must verify BASIC pure workspace tasks, PRO Planner direct `termux_shell` usage, pure UI regression coverage, and mixed UI plus workspace tasks.
- `ts-qa-ordering-cancel`: requires a physical Android device with Termux. Human QA must verify live turn ordering with `mobile_action` plus `termux_shell`, and verify stopping a long `termux_shell` command kills the Termux subprocess promptly through OkHttp cancel / TCP disconnect.
- `ts-qa-bootstrap`: requires a physical Android device with Termux and failure-mode manipulation. Human QA must verify Termux not installed, RUN_COMMAND permission missing, allow-external-apps disabled, package install failure/recovery, deploy/version mismatch, bridge start/health failure, port conflict, typed Settings UI reasons, and checkpoint/reload with a fresh snapshot.
- Non-device gap worth adding before merge: there are no JVM or instrumentation tests for the cold-start manager state to session snapshot path, which is the high finding above.
- Non-device gap worth adding after the blocker: the settings row has no Compose test for every status/reason string, row click behavior, F-Droid fallback, setup/restart dispatch, or toggle persistence.
- Non-device gap worth adding after the blocker: `TermuxBridgeManager` bootstrap transitions and reason mapping remain hard to test because the manager constructs its concrete RUN_COMMAND adapter and health client internally. A fakeable adapter/client seam would allow deterministic JVM tests for setup cancellation, passive health, and reason preservation.

# Review: settings_platform_mode

## High

1. Do not implement "persist intended, render effective" only inside Settings. Today `platformMode` is a single persisted intent, copied into `SessionConfig`, then pushed into `AgentService` and overlay state. `PlatformFactory` can fall back to `AccessibilityPlatform`, but nothing publishes that effective result back out, so Settings/Home/capsule can disagree with the actual platform. Introduce a first-class `effectivePlatformMode` from the instantiated `AndroidPlatform` and feed every renderer from it, or keep rendering the persisted intent everywhere. (doc/todo/settings_platform_mode/design_claude.md:55-62,71-73,141-142; app/src/main/kotlin/ai/closepaw/protocol/SessionConfig.kt:51-52; app/src/main/kotlin/ai/closepaw/app/AppSettingsState.kt:33,110-113; app/src/main/kotlin/ai/closepaw/app/MainActivity.kt:578,640-663; app/src/main/kotlin/ai/closepaw/app/AgentService.kt:89-101; app/src/main/kotlin/ai/closepaw/app/ServiceOverlayController.kt:135-165; app/src/main/kotlin/ai/closepaw/platform/PlatformFactory.kt:45-55)

2. Define the selector/status as "next session availability", not "live session mode", unless you also plumb runtime failure state into the UI. A running `VirtualDisplayPlatform` does not hot-swap to accessibility on binder death; it marks itself broken. The doc currently says binder-dead should snap the selector to Accessibility and that runtime behavior stays consistent with that visual, which is false for an in-flight VD session. (doc/todo/settings_platform_mode/design_claude.md:55-62; app/src/main/kotlin/ai/closepaw/platform/PlatformFactory.kt:21-22,50-55; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/VirtualDisplayPlatform.kt:168-176; app/src/main/kotlin/ai/closepaw/app/MainActivity.kt:578; app/src/main/kotlin/ai/closepaw/app/AgentService.kt:97-100)

## Medium

1. Do not do binder pings in composition and claim recomposition only happens on resume. `AppSettingsState` exposes Compose state for `debugMode`, `traceEnabled`, and `platformMode`, `SettingsSheet` feeds those values into `PermissionsAdvancedSettingsPage`, and that page mutates switches plus local dialog state. Any of that can recompose the row. Put Shizuku reads behind a remembered state producer and refresh only from `ON_RESUME` and listener callbacks. (doc/todo/settings_platform_mode/design_claude.md:23-25,79-82; app/src/main/kotlin/ai/closepaw/app/AppSettingsState.kt:17-35,90-113; app/src/main/kotlin/ai/closepaw/ui/settings/SettingsSheet.kt:131-141; app/src/main/kotlin/ai/closepaw/ui/settings/PermissionsAdvancedSettingsPage.kt:87-125,147-211)

2. Pick one owner for Shizuku status and keep UI code in the UI layer. The doc currently says status is derived in the Composable, that `DisplayModeSection` calls `rememberShizukuStatus()`, and that `SettingsSheet` receives a `shizukuStatus` flow plus request lambda from the Activity. That is split ownership for one transient bit. `ShizukuClient.requestPermission()` already needs no `Activity`, and current settings wiring already passes plain values/callbacks through `MainActivityContent` -> `SettingsSheet` -> page. Keep the observer local to settings UI and bubble up only `onPlatformModeChange`. Keep the composable observer out of `platform/virtualdisplay`. (doc/todo/settings_platform_mode/design_claude.md:23-25,70-82,102-103; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/ShizukuClient.kt:11-18,41-54; app/src/main/kotlin/ai/closepaw/app/MainActivityContent.kt:98-136; app/src/main/kotlin/ai/closepaw/ui/settings/SettingsSheet.kt:31-64,131-141)

3. Add symmetric wrapper methods for the permission-result listener and unregister both listeners in one `DisposableEffect`. The current wrapper already models binder-death add/remove, but it has no permission-result listener API. Do not call `Shizuku.addRequestPermissionResultListener` straight from UI code; keep Shizuku runtime hooks behind `ShizukuClient` / `ShizukuRuntimeGateway` and make unregister explicit. (doc/todo/settings_platform_mode/design_claude.md:25,79-82; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/ShizukuClient.kt:29-54; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/ShizukuRuntimeGateway.kt:9-43)

4. Say `SharedPreferences`, not DataStore. `platformMode` lives in `AppSettingsStore` under `agent_prefs`, so the doc currently names the wrong storage layer. Keep the "no new key" decision, but anchor it to the real code. (doc/todo/settings_platform_mode/design_claude.md:23; app/src/main/kotlin/ai/closepaw/app/AppSettingsStore.kt:23-52,88-149)

5. Do not put `VD` into the Home subtitle from `settingsState.platformMode`. That value is persisted intent, not effective mode, so it will contradict the selector as soon as Shizuku is down. Feed the subtitle from the same effective-mode source as the selector, or leave mode out of Home until that source exists. (doc/todo/settings_platform_mode/design_claude.md:61-73; app/src/main/kotlin/ai/closepaw/ui/settings/SettingsHomePage.kt:58-61,112-123)

## Validated

- Keep Shizuku status coupled to Display Mode, not as a free-standing permissions fact. In this codebase Shizuku only gates `VIRTUAL_DISPLAY` creation, and the current page has no independent Shizuku surface. Put the explanation next to the disabled option. (doc/todo/settings_platform_mode/design_claude.md:16-21,137-140; app/src/main/kotlin/ai/closepaw/ui/settings/PermissionsAdvancedSettingsPage.kt:70-87; app/src/main/kotlin/ai/closepaw/platform/PlatformFactory.kt:68-76)

- Use `ON_RESUME` plus Shizuku listeners; do not poll. Availability and permission are direct runtime checks, and the state changes happen outside the app. Event-driven refresh is the right model once the observer is stateful and properly disposed. (doc/todo/settings_platform_mode/design_claude.md:25-27,139-140; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/ShizukuClient.kt:33-54; app/src/main/kotlin/ai/closepaw/platform/virtualdisplay/ShizukuRuntimeGateway.kt:15-35)

- Keep rejecting an app-tier global override. App tiers come from static `security/app_tiers.json`, unknown apps default to `CAUTIOUS`, `BLOCKED` is an absolute deny, and the existing approval flow already provides `SESSION` / `ALWAYS` escape hatches for non-blocked apps. A settings-level override would cut across that policy. (doc/todo/settings_platform_mode/design_claude.md:10,88-90,142; app/src/main/kotlin/ai/closepaw/tool/AppClassifier.kt:12-20,40-66; app/src/main/kotlin/ai/closepaw/tool/PolicyEngine.kt:13-20,64-89,107-124; app/src/main/kotlin/ai/closepaw/session/AgentSession.kt:647-653)

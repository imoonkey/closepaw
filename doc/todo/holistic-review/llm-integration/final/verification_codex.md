## Real Problems (confirmed in code)
- `#1` Domain exceptions are not preserved in streaming retry. `CloudStreamRetryRunner.kt:50-57` always reclassifies through `OpenAIErrorClassifier.classify()`, and `OpenAIErrorClassifier.kt:11-52` has no fast-path for existing `RateLimitException` or `TransientException`, so typed Codex errors from `CodexResponseClient.kt:243-263` can lose retryability. Proposed fix is KISS: short-circuit already-classified domain exceptions before reclassification.
- `#2` `Created` currently blocks safe retry. `CloudStreamRetryRunner.kt:33-40` marks every emitted event as output, and `CloudStreamRetryPolicy.kt:22-29` refuses retry after any emitted event, so a stream that only emitted `LLMStreamEvent.Created` will not retry. Proposed fix is KISS: track semantic output (`TextDelta` and completed tool calls), not any event.
- `#3` Codex treats `response.incomplete` as success. Both `CodexResponseClient.kt:95-97` and `CodexSseParser.kt:95-97` fold `response.incomplete` into normal completion. Proposed fix is mostly KISS: fail immediately on `response.incomplete` and surface the backend reason instead of marking the turn successful.
- `#4` `ChatCompletionClient` emits `Completed` without proving the stream reached a terminal chunk. `ChatCompletionClient.kt:190-219` logs output and emits `LLMStreamEvent.Completed` after any clean EOF, even if no `finishReason` was ever seen. Proposed fix is KISS: track a `sawFinishReason` flag and fail if the stream ends without one.
- `#5` Two streaming paths throw the wrong exception type on premature EOF. `OpenAIResponseClient.kt:152-154` and `CodexResponseClient.kt:176-177` throw `RuntimeException("Stream ended without completion event")`, which disables retry for a transient network drop. Proposed fix is KISS: throw `TransientException` instead.
- `#6` Error classification is too fragile and leaks OpenAI-specific heuristics into Codex retry handling. `OpenAIErrorClassifier.kt:15-50` relies on string matching, `CloudStreamRetryRunner.kt:50-57` applies it to every streaming exception, and `CodexResponseClient.kt:243-263` already produces typed domain exceptions that should not be remapped. Proposed fix is directionally right; the KISS version is to preserve existing domain exceptions and add typed OpenAI SDK branches before any string fallback.
- `#7` Debug SSL really trusts all server certificates. `app/src/debug/kotlin/com/moonkey/androidagent/llm/InsecureSslConfig.kt:24-35` accepts every cert and key pair; only the source-set split keeps this out of release (`app/src/release/kotlin/com/moonkey/androidagent/llm/InsecureSslConfig.kt`). The review's "date validation" wording is slightly off, but the security issue is real. Proposed fix is KISS: require an explicit eval-only opt-in before wiring the insecure trust manager.
- `#8` Streaming cancellation is not explicitly propagated. `CodexSseParser.kt:22-60` blocks on `BufferedReader.readLine()`, `CodexResponseClient.kt:145-196` does not retain/cancel the underlying `Call`, and the SDK-backed streams in `OpenAIResponseClient.kt:101-173` and `ChatCompletionClient.kt:132-232` have no explicit cancellation check or close path. Real problem; the proposed fix is directionally right, but the most important KISS step is to propagate cancellation and cancel the underlying network stream.
- `#9` The Responses-family split is at the wrong seam. `LLMClientFactory.kt:56-62` treats `OpenAIResponseClient` and `CodexResponseClient` as peer client types even though both expose the same Responses semantics and duplicate stream accumulation/completion logic in `OpenAIResponseClient.kt` and `CodexResponseClient.kt`. Real maintainability problem, but the full transport-family collapse is not the KISSest first move.
- `#10` Local-backend capability loss is real and implicit. In `LFMLLMClient.kt:294-299`, developer/system history roles are dropped; `LFMLLMClient.kt:299` feeds `EasyInputMessage.Content` through `extractMessageContent(Any)`; `LFMLLMClient.kt:319-324` drops function-output call IDs; and `LFMLLMClient.kt:342-345` invents random tool call IDs. The unsupported semantics exist in code and are not declared anywhere. Proposed fix is directionally right, but a narrower explicit capability surface would be more KISS than a broad rollout.
- `#12` Tool-parameter parsing is duplicated. `CodexRequestBuilder.kt:153-174` and `LeapFunctionInterop.kt:22-65` repeat the same known/unknown/raw-JSON parsing flow, differing mainly in logging and fallback behavior. Proposed fix is KISS: extract one helper that returns `JSONObject?` and let each caller decide its fallback.
- `#13` The post-retry `callbackFlow` epilogue is duplicated in three clients. The same `retryResult.completed / failureEmitted / trySend(Failed)` block appears in `OpenAIResponseClient.kt:159-168`, `CodexResponseClient.kt:184-192`, and `ChatCompletionClient.kt:222-229`. Real but low-value; a tiny helper is fine, although it may be simpler to let later Responses cleanup remove the duplication naturally.
- `#14` Message-content extraction is duplicated, and the shared helper is wrong for its current call sites. `MessageContentExtractor.kt:4-16` takes `Any`, but its active callers in `LFMLLMClient.kt:299`, `LlmLogger.kt:33`, and `trace/LlmInputItemsTraceSerializer.kt:25` pass `EasyInputMessage.Content`, so the helper falls through to `toString()` instead of extracting text. This is more than deduplication: `LFMLLMClient` is currently feeding wrapper strings like `Content{textInput=...}` into Leap. The proposed fix is not quite KISS because `ChatCompletionInterop.extractStringContent()` lives in a chat-specific file and there is a third trace call site.

## False Positives (claimed bug doesn't exist)
- `#11` The review claims there is a clean shared `JsonValueConverter` to extract from `CodexRequestBuilder.kt:176-191` and `LeapFunctionInterop.kt:193-230`. Actual code has only partial overlap: Codex preserves explicit nulls with `JSONObject.NULL`, while Leap returns Kotlin `null` and also reparses raw JSON-string payloads into `JSONObject`/`JSONArray`. That is related logic, not a drop-in shared utility yet.
- `#15` The review frames an internal canonical request model as a future cleanup target, but there is no present code defect that proves it is needed now. The current codebase shows some duplication across `ChatCompletionInterop.kt`, `CodexRequestBuilder.kt`, and `LFMLLMClient.kt`, but not enough to justify another mandatory abstraction before the smaller concrete fixes land.

## Overstated (real but wrong severity)
- None. I found a few wording issues, but no finding where the underlying issue existed and the stated severity was clearly wrong.

## Simpler Alternatives
- `#3` In both Codex paths, branch on `response.incomplete` immediately and emit/throw failure there; no extra partial-success state machine is needed.
- `#6` Keep one OpenAI classifier for SDK errors, but add fast-paths for existing domain exceptions and typed SDK exceptions; do not introduce a larger transport-classifier layer yet.
- `#8` First fix cancellation propagation: rethrow `CancellationException`, keep a handle to the underlying `Call` or stream, and cancel it from `awaitClose`; `ensureActive()` only helps once the loop regains control.
- `#9` Extract small shared Responses helpers first: request/result accumulation, completion checks, and retry epilogue handling. Only collapse the client taxonomy if that still leaves meaningful duplication.
- `#10` Start with the capability differences the rest of the app actually needs to reason about, or a small `LocalLlmSemantics` object, before introducing a broad `LlmCapabilities` surface.
- `#13` If the three retry epilogues survive the P0/P1 fixes, use one tiny private helper; otherwise let the larger Responses cleanup delete the duplication naturally.
- `#14` Keep a dedicated shared content extractor, but make it typed on `EasyInputMessage.Content` and reuse it from `ChatCompletionInterop`, `LFMLLMClient`, `LlmLogger`, and `LlmInputItemsTraceSerializer`.

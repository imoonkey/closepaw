## High
1. **`Op.Takeover` still races with task completion, so the post-turn state is not deterministic.** [AgentSession.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/AgentSession.kt:364), [AgentSession.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/AgentSession.kt:426), [Agent.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/Agent.kt:156), [Op.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/protocol/Op.kt:18), [AgentSessionTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/session/AgentSessionTest.kt:197)

   `handleTakeover()` sets `TakeoverPending`, releases `lifecycleMutex`, and then waits on the pause confirmation. If the current turn also completes the task, `Agent.run()` completes that pause deferred in `finally` before `SessionAgentRunner` enqueues the runner completion. That leaves `handleTakeover()` and `handleAgentComplete()` competing to reacquire `lifecycleMutex` after the same turn. If takeover wins, the session can emit `SessionTakeover` and then immediately get forced to `Idle` by `handleAgentComplete()`. If completion wins, takeover disappears entirely. Either outcome violates the design goal of having one serialized lifecycle path and still does not cleanly satisfy the `Op.Takeover` contract that the session transitions to `Paused` once the current action finishes. The new test suite currently codifies this nondeterminism instead of rejecting it by explicitly allowing `Paused` to appear or not.

2. **The new token model does not provide “real cancellation” for built-in long-running tools, especially `delegate_task`.** [ToolRouter.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/ToolRouter.kt:347), [ToolRouter.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/ToolRouter.kt:359), [DelegateTaskTool.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/impl/DelegateTaskTool.kt:144), [SubAgentRunner.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/subagent/SubAgentRunner.kt:61), [ToolRouterTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/tool/ToolRouterTest.kt:132)

   `ToolRouter.cancel()` and `cancelAll()` now only flip a per-call token and rely on the invocation continuing to poll `context.isCancelled()`. That is enough for the synthetic `CancellableToolSpec` used in the tests, but not for actual long-running tools. `DelegateTaskInvocation.execute()` checks cancellation once and then blocks in `runnerFactory(roleDef).run(...)`; the child runner creates a separate child agent/router with no linkage back to the parent token while still sharing parent resources such as the platform and session scratchpad. During session cleanup, the parent router can therefore report the call as “cancelling” while the delegated sub-agent keeps running against torn-down shared services until it times out or finishes on its own. That falls short of the Phase 4 acceptance criteria: cancellation is still cooperative only for specially-written tools, not for the real built-ins that matter.

## Medium
1. **Introducing `TakeoverPending` broke the existing queued-input contract in `SessionCoordinator`.** [SessionState.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/protocol/SessionState.kt:42), [AgentSession.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/AgentSession.kt:282), [SessionCoordinator.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionCoordinator.kt:51), [MainActivity.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/app/MainActivity.kt:431)

   `SessionCoordinator.submit()` still treats only `Running` and `Paused` as busy. With the new state machine, `TakeoverPending` falls into the “send immediately” branch and returns `SENT`, but `AgentSession.handleUserInput()` rejects user input in `TakeoverPending` as busy. Existing callers that rely on the coordinator to queue follow-up input during busy periods now silently drop those inputs during takeover handoff instead of queueing them for later drain.

2. **The Phase 6 off-main bootstrap hardening breaks at least one live caller.** [SessionLlmBootstrapper.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionLlmBootstrapper.kt:90), [DefaultOnboardingDemoController.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/onboarding/DefaultOnboardingDemoController.kt:91), [MainActivity.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/app/MainActivity.kt:160), [SessionLlmBootstrapperTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/session/SessionLlmBootstrapperTest.kt:17)

   `SessionLlmBootstrapper.create()` now throws on the main thread, which is a reasonable invariant. But this diff does not move every caller off-main. `DefaultOnboardingDemoController` still calls `AgentSession.create()` directly from the `lifecycleScope` passed in by `MainActivity`, so the new invariant turns onboarding-demo startup into an `IllegalStateException` at runtime. The new test validates the throw, but there is no corresponding caller fix.

3. **The new tests do not actually validate several of the design doc’s load-bearing invariants.** [SessionRecordingServiceTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/history/SessionRecordingServiceTest.kt:242), [ToolRouterTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/tool/ToolRouterTest.kt:132), [AgentSessionTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/session/AgentSessionTest.kt:198), [AgentSessionTest.kt](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/test/kotlin/com/moonkey/androidagent/session/AgentSessionTest.kt:340)

   The recorder test named “later revision wins regardless of completion order” never inverts write completion order; it uses the real `SessionStorage` with no injected delay, so it would still pass even if revision checks were ineffective as long as the second save simply runs later. The router tests only exercise a synthetic tool that polls `isCancelled()` every 100ms, not built-ins like `delegate_task` or `ask_user`. The takeover test explicitly allows `Paused` to appear or not, which means it blesses the nondeterminism described above instead of guarding against it. And the lifecycle tests use a relaxed mocked `recordingService`, so they do not cover the interaction between lifecycle serialization and real checkpoint I/O at all.

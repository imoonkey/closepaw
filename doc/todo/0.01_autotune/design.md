# AutoTune Design

## What is this?

A feedback loop: **fix code → run eval → analyze → wait for human → repeat**. Today you drive every step manually. Most steps don't need you — only the "review analysis & approve next steps" step does.

## First Principles

1. **The loop is the unit of work.** Everything else is bookkeeping.
2. **Human = quality gate, not crank-turner.** Automate the crank, gate on the decisions.
3. **Progress must be observable without being in the loop.** If you can't glance at a board and know where things stand, the automation is a black box.
4. **Agent picks the task list.** No manual grouping. The agent decides what to run based on what it changed — just like a human would.

## Design

### The Loop (one `/autotune` invocation)

```
┌──────────────────────────────────────────────────────┐
│                    /autotune                          │
│                                                      │
│  1. FIX ──► 2. PREPARE ──► 3. RUN ──► 4. ANALYZE    │
│                                                      │
│  ──► STOP (human reviews analysis + next steps)      │
│                                                      │
│  human approves ──► next /autotune invocation         │
└──────────────────────────────────────────────────────┘
```

**Step 1 — Fix**: Apply changes from the previous round's approved next steps.
- Follow `sop/code_work.md`.
- Commit with conventional commit message linking to round.
- On round 0 (first run), skip this step — nothing to fix yet.

**Step 2 — Prepare**: Agent builds the task list for this round.
- Agent reasons: "I changed X, which should affect tasks A, B, C. I also want to spot-check D for regressions."
- Subtract `eval/config/cannot_handle_group.txt`. (human can update this with known unfixable tasks to save eval budget)
- Write to `eval/config/autotune_round_N.txt`.
- Full task universe: `eval/config/aw_fullset.txt` (`aw_subset_group_0.txt` through `aw_subset_group_5.txt` combined — the groups were a manual cost-control split, not a semantic boundary). Agent selects a subset each round based on relevance.

**Step 3 — Run**: Execute eval runner.
- `eval/.venv/bin/python eval/aw_bridge/runner.py --tasks-file <file>`
- Monitor for stalls (no output for X minutes → alert or auto-recover).
- Output: `eval/results/<run_id>/`

**Step 4 — Analyze**: Run `/cog-tune` on every task in the run.
- Per-task analysis → `doc/autotune/round_N/<run_id>/per_task/*_<agent>.md`
- Round summary → `doc/autotune/round_N/<run_id>/common_problems_<agent>.md`
  - Includes: common failure patterns, root cause categories, **and a `## Next Steps` section with proposed fixes for the next round**.
- Run `scripts/scoreboard.py` to regenerate scoreboard from eval results.
- Update changelog, global issues, and per-task changelogs.
- Optionally: dual-agent analysis (Claude + Codex) + `/align`. Config flag, off by default.

**STOP**: Present summary to human. Wait for approval of next steps before the next `/autotune`.

### Task Selection Heuristics (Step 2)

The agent picks tasks using simple rules:

1. **Directly affected**: Tasks whose failure root cause matches what was just fixed. (e.g., fixed `type clear=false` → re-run all `ActionFailure` tasks that involved text input)
2. (Optional) **Regression canaries**: A few previously-passing tasks to make sure nothing broke. Pick randomly or round-robin from the passing set.
3. (Optional) **Stuck tasks**: Optionally re-test a stuck task if the agent has a new idea.
4. **Budget**: Keep each round to a reasonable token budget (agent judges, but ~5-10 tasks as a guideline, and 20 for larger iterations after multiple rounds of fixes, to test for regressions).

### The Scoreboard

**Source of truth**: `doc/autotune/meta/scoreboard.json` — generated by `scripts/scoreboard.py` from `eval/results/*/per_task.jsonl`.

No hand-editing. Run the script, get the board.

```json
{
  "tasks": {
    "MarkorEditNote": {
      "runs": {
        "20260227_161048": { "score": 0.0, "status": "completed", "turns": 22 },
        "20260227_222506": { "score": 0.0, "status": "completed", "turns": 18 },
        "20260301_012237": { "score": 1.0, "status": "completed", "turns": 12 }
      },
      "recent_rate": "1/3",
      "status": "improving"
    },
    "OsmAndMarker": {
      "runs": {
        "20260227_161048": { "score": 0.0, "status": "completed", "turns": 30 },
        "20260301_012237": { "score": 0.0, "status": "completed", "turns": 28 }
      },
      "recent_rate": "0/2",
      "status": "stuck"
    }
  },
  "runs": {
    "20260227_161048": { "round": 1, "total": 20, "passed": 7, "rate": 0.35 },
    "20260227_222506": { "round": 2, "total": 28, "passed": 14, "rate": 0.519 },
    "20260301_012237": { "round": 3, "total": 15, "passed": 2, "rate": 0.133 }
  }
}
```

**Key rules**:
- Tasks only have entries for runs they participated in. No nulls, no blanks — sparse by default.
- `recent_rate` = success in last min(3, total_runs) runs.
- `status` derived: `fixed` (recent_rate = 100%), `improving` (last run better than previous), `stuck` (≥3 runs at 0%), `regressed` (last run worse), `new` (first run).
- The script also writes a markdown table to `doc/autotune/meta/scoreboard.md` for human readability. JSON is SOT; markdown is a rendered view.

#### `scripts/scoreboard.py`

```
Usage: python scripts/scoreboard.py [--run-id <id>]

Scans eval/results/*/per_task.jsonl, builds the scoreboard.
Writes: doc/autotune/meta/scoreboard.json (SOT)
        doc/autotune/meta/scoreboard.md  (rendered view)
  --run-id Only include specific run(s), comma-separated
```

### Global Issues

`doc/autotune/meta/issues.md` — manually curated by agent, reviewed by human.

```markdown
# Global Issues

## Open
- [ ] **Turn exhaustion on multi-item tasks** — 4 tasks affected. Options: raise max_turns or batch operations.
- [ ] **OsmAnd a11y fundamentally broken** — map UI inaccessible. Candidate for cannot_handle.

## Resolved
- [x] **type clear=false for edit fields** — fixed R3 (commit abc123)
- [x] **LLM timeout on calendar queries** — fixed R3 (infra retry)

## Parked (cannot_handle)
- MarkorTranscribeVideo — requires vision capability we don't have
```

### Per-Task Changelog

`doc/autotune/meta/per_task/<TaskName>.md` — lightweight longitudinal view per task. Appended each round the task runs. Not a full analysis — just the delta.

```markdown
# MarkorEditNote

## R3 (20260301_012237) — PASS (was: FAIL)
- Score: 1.0 (prev: 0.0)
- Turns: 12 (prev: 18)
- What changed: P1 fix (type clear=false) resolved the text duplication issue. Agent now preserves existing text when editing.

## R2 (20260227_222506) — FAIL
- Score: 0.0
- Turns: 18
- Root cause: ActionFailure — type action cleared existing text before typing new content.

## R1 (20260227_161048) — FAIL
- Score: 0.0
- Turns: 22
- Root cause: ActionFailure — same text clearing issue. Also wasted turns retrying the same approach.
```

**Rules**:
- Newest round on top.
- 2-4 lines per entry: score, turns, one-line behavior delta.
- Link to full analysis: "See `round_N/<run_id>/per_task/<TaskName>_<agent>.md` for details."
- Agent writes this during Step 4 (Analyze), after completing the full per-task analysis.

## What's NOT in scope (KISS)

- **No custom UI / dashboard tool.** `meta/scoreboard.md` is the dashboard.
- **No database.** `eval/results/` is the database. The script reads it directly.
- **No manual task grouping.** Agent picks tasks autonomously.
- **No auto-approve.** Every `/autotune` stops after analysis. Human reviews before next invocation.

## Implementation Order

1. **`scripts/scoreboard.py`** — immediate value. Reads existing `eval/results/`, outputs JSON + markdown.
2. **Meta files** — bootstrap `issues.md` and `changelog.md` from existing round data.
3. **The loop skeleton** — skill that chains Steps 1-4, stops for review.
4. **Stall detection** — monitor eval runner, alert on hang.
5. **Dual-agent mode** — optional Claude+Codex analysis + align.

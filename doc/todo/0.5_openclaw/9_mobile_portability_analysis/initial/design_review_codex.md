# Review: 9_mobile_portability_analysis / design_claude

## High

1. **The session-persistence proposal is built on an incorrect baseline and would duplicate existing owners.** The design says current sessions are "largely transient" and proposes adding JSONL persistence plus a new structured `SessionId` model to the session core ([design_claude.md:70](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L70), [design_claude.md:194](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L194)). But the repo already has `Hot Idle` follow-up continuity, checkpoint-based reload, `SessionRecordingService` for persisted history, `SessionStorage` for file I/O, and a single `SessionId` value class used across protocol/runtime ([session.md:58](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/main/infra/session.md#L58), [session.md:64](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/main/infra/session.md#L64), [session.md:80](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/main/infra/session.md#L80), [SessionHistoryBootstrapper.kt:18](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionHistoryBootstrapper.kt#L18), [SessionId.kt:1](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/protocol/SessionId.kt#L1)). Pushing JSONL persistence into `HistoryManager` also cuts across an explicit architecture boundary: `HistoryManager` is the runtime prompt-history/compression owner, while persistence lives in recording/storage services. The design should start from the existing split and extend it, not replace it with a second session/persistence model.

2. **Dynamic tool registration is not compatible with the current session-scoped agent contract as written.** The design proposes recomputing active tools on permission changes and replacing the registry at runtime ([design_claude.md:125](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L125), [design_claude.md:197](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L197)). But `SessionAgentRunner` freezes `allowedToolNames` at agent start from the selected `AgentDef`, and `Turn` builds tool schemas every turn by intersecting the registry with that fixed allowlist ([SessionAgentRunner.kt:50](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionAgentRunner.kt#L50), [SessionAgentRunner.kt:66](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionAgentRunner.kt#L66), [Turn.kt:154](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/Turn.kt#L154), [Turn.kt:188](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/Turn.kt#L188)). `ToolRegistry` also has no `replaceAll`; it supports register/unregister/clear, which would make mid-session mutation observable but not principled ([ToolRegistry.kt:32](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/ToolRegistry.kt#L32), [ToolRegistry.kt:53](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/ToolRegistry.kt#L53), [ToolRegistry.kt:92](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/ToolRegistry.kt#L92)). The design needs a clear rule: either capabilities are snapshotted per task/session, or capability changes trigger an agent restart/rebind. Without that, tool availability becomes nondeterministic across turns.

## Medium

1. **The design conflates session memory with app-skill injection instead of preserving the repo’s ownership layers.** The memory proposal says to extend `buildAppSkillMessage()` so retrieved memory is injected "alongside static skills" ([design_claude.md:65](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L65)). In the current architecture, app skills are authored per-package guidance loaded by `TurnPlanningPhaseRunner`, while `PromptBuilder` separately owns working-memory injection ([TurnPlanningPhaseRunner.kt:71](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/TurnPlanningPhaseRunner.kt#L71), [TurnPlanningPhaseRunner.kt:158](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/TurnPlanningPhaseRunner.kt#L158), [PromptBuilder.kt:20](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/cognition/prompt/PromptBuilder.kt#L20), [PromptBuilder.kt:43](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/agent/cognition/prompt/PromptBuilder.kt#L43)). Mixing retrieved, mutable memory into the app-skill channel weakens debuggability and prompt ownership. A cleaner design is a separate "retrieved memory" block between working memory and app skill, or between app skill and observation, rather than overloading the app-skill mechanism.

2. **The "collect mode" claim overstates what the current queue actually does, leaving the new behavior unspecified.** The design says merged queued input is "already partially implemented in `SessionCoordinator`'s drain pattern" ([design_claude.md:91](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L91)). The current coordinator only appends raw strings while running and replays them one-by-one when the session becomes idle; there is no merge/canonicalization logic at all ([SessionCoordinator.kt:63](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionCoordinator.kt#L63), [SessionCoordinator.kt:119](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionCoordinator.kt#L119), [SessionCoordinator.kt:210](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/session/SessionCoordinator.kt#L210)). If merged follow-up input matters, the design needs to specify the canonical representation and semantics: append as one `Op.Supplement`, coalesce only adjacent user texts, or preserve ordered independent tasks.

3. **The shell/tool portability section drifts beyond the current tool boundary.** Claude suggests adapting shell toward "file I/O + package manager intents" ([design_claude.md:23](/Users/moonkey/workspace/android-agent-workspace/androidagent/doc/todo/0.5_openclaw/9_mobile_portability_analysis/initial/design_claude.md#L23)), but the existing `ShellTool` is explicitly file-inspection-only and blocks `pm`/`am` style command paths ([ShellTool.kt:21](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/impl/ShellTool.kt#L21), [ShellTool.kt:77](/Users/moonkey/workspace/android-agent-workspace/androidagent/app/src/main/kotlin/com/moonkey/androidagent/tool/impl/ShellTool.kt#L77)). That may still be the right long-term boundary, but the review doc should call out that "package manager intents" are not an incremental extension of the current shell model; they would need a separate native tool or app-control API.

## Summary

Claude’s main thesis is correct: absorb OpenClaw’s portable patterns and reject the desktop runtime. The strongest parts are the non-goals, the relay reversal, and the emphasis on Android-native memory/security/capability layers.

The main weakness is that several proposed extensions are framed as small increments on top of the current repo, but they actually cross existing architectural boundaries:

- runtime history vs persisted session recording
- authored app skills vs retrieved memory
- static per-agent tool contracts vs hot-swapped capability sets

Those boundaries should be kept explicit in the next iteration.

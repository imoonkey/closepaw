# Review: `design_claude.md`

## Summary

The design is directionally correct on the main goal: stop exposing tools purely because they exist in code, and move availability checks ahead of planning. The main problems are in integration with the current multi-agent architecture and in the execution-time safety story. As written, the proposal would either hide required tools from some agents or still allow stale tool calls after capability loss.

## High

1. Global `allowedToolNames` inside `DynamicToolRegistry` conflicts with the current per-agent and sub-agent filtering model. In the proposal, `DynamicToolRegistry` is constructed with a single `allowedToolNames` set and only registers tools inside that set, then `Turn` is pointed at that pre-filtered registry. That does not fit the current architecture, where the session owns one shared registry and each agent applies its own allowlist later (`SessionAgentRunner` passes `allowedToolNames` into `AgentExecutionConfig`, `Turn` filters again at request time, and sub-agents create filtered child registries from the parent session registry). If the dynamic registry is bootstrapped with planner tools, the executor loses `mobile_action`; if it is bootstrapped with executor tools, the planner unnecessarily sees executor-only tools unless more ad hoc filtering is added. This needs to stay as `capability filtering` composed with existing `agent allowlist` filtering, not replace it. Without providers for those tools, the new registry cannot preserve current planner and standalone behavior. 3. The execution-time safety net is not strong enough for approval waits or mid-turn capability loss. The design refreshes only at planning time, then claims `ToolRouter.execute()` is guaranteed to see a valid tool because the registry was already refreshed. That is false in the current flow: `ToolRouter` can spend up to 60 seconds waiting for approval before executing, and capability can change during that window. The proposed one-line `contains()` check does not fix that unless the registry is refreshed again immediately before execution; otherwise it is just checking stale state. The design needs an execution-time availability re-evaluation step, not only a membership test against the last refresh. References: Claude design lines 188-206, 242-243, and 275-283; current behavior in `ToolRouter` lines 113-170 and 214-235.

## Medium

1. Grouping tools into shared providers weakens the brief's "each tool owns its availability" principle and already blurs capability boundaries for `open_app`. The design groups `mobile_action`, `system_button`, and `open_app` into one `AccessibilityToolProvider`, but `open_app` is implemented through the `AndroidPlatform` app-management APIs (`getInstalledApps`, `getCurrentPackageName`, `launchApp`) rather than raw touch/a11y action dispatch. That makes this grouping convenient, but it hardcodes a dependency bundle that may diverge as platforms evolve. A better design keeps tool-local availability decisions while allowing shared helper predicates under the hood. References: Claude design lines 58-94; current `OpenAppTool` behavior lines 148-215 and platform app-management abstraction in `AndroidPlatform`.

2. The wrapper approach leaves an unresolved hole around `createFilteredCopy()` and child registries. The design says `ToolRegistry.kt` remains unchanged and `DynamicToolRegistry` wraps it, but the current sub-agent path directly calls `createFilteredCopy()` on `ToolRegistry` to build a child registry. The review draft should either explain how dynamic capability behavior propagates into child registries or explicitly replace that path. Without that, the design is incomplete for the existing delegation flow. References: Claude design lines 137-145 and 307-308; current behavior in `SubAgentRunner` lines 122-130.

## Recommendation

`CHANGES_REQUESTED`

The design should be revised before implementation. The main fixes are:

1. Keep capability filtering separate from per-agent allowlists.
2. Cover all current tools, especially `ask_user` and `delegate_task`.
3. Add a real execution-time capability recheck, not just a stale registry membership test.
4. Specify how delegation/sub-agent filtered registries continue to work.

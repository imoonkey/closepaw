## Evidence: The dispatchGesture Regression

### Code Changes Between Runs

**Commit `e745664`** (fix: harden dispatchGesture tap path and add diagnostics) introduced:

1. **`setDisplayId()` in `buildGesture()`** (line 157-164 of AccessibilityGestureInjector.kt):
   ```kotlin
   private fun buildGesture(stroke: StrokeDescription): GestureDescription {
       val builder = GestureDescription.Builder().addStroke(stroke)
       if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R) {
           val displayId = resolveDisplayId() ?: Display.DEFAULT_DISPLAY
           builder.setDisplayId(displayId)
       }
       return builder.build()
   }
   ```

2. **`resolveDisplayId()` queries active window** (line 166-169):
   ```kotlin
   private fun resolveDisplayId(): Int? {
       if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) return null
       return service.rootInActiveWindow?.window?.displayId
   }
   ```

3. **Explicit `Handler(Looper.getMainLooper())` for callback** (line 143):
   ```kotlin
   service.dispatchGesture(gesture, callback, Handler(Looper.getMainLooper()))
   ```

### Why `setDisplayId()` Is the Primary Suspect

- **Before the change**: `GestureDescription.Builder.build()` uses `Display.DEFAULT_DISPLAY` implicitly
- **After the change**: Queries `service.rootInActiveWindow?.window?.displayId` which can return unexpected values:
  - When a dialog/overlay is visible (like brightness slider dialog), the "active window" may differ
  - The `window` property on accessibility nodes can reference virtual displays or sub-windows
  - If `rootInActiveWindow` is null, it falls back to `DEFAULT_DISPLAY` — but if it's non-null and returns a non-default display ID, the gesture gets dispatched to the wrong display
- **All gesture types affected**: `injectTap`, `injectSwipe`, `injectLongPress` all go through `buildGesture()`
- **Node actions are unaffected**: `NodeActionPerformer.performAction()` bypasses `dispatchGesture` entirely

### Cross-Reference with debug3/ Findings

The debug3 documents confirm the same `dispatchGesture` reliability pattern:
- `dispatchGesture` reports "Gesture completed" but UI unchanged
- Node actions (`performAction`) work at same coordinates
- ADB `input swipe` works at same coordinates
- The `setDisplayId()` fix was specifically added during debug3 to address display routing — but may have overcorrected

## Recommendations

### Immediate Fix (P0): `setDisplayId()` guard

The `resolveDisplayId()` function should be more cautious:

```kotlin
private fun resolveDisplayId(): Int? {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) return null
    val displayId = service.rootInActiveWindow?.window?.displayId
    // Only override if we get a valid non-default ID
    // For now, always use DEFAULT_DISPLAY until display routing is proven reliable
    return if (displayId != null && displayId != Display.DEFAULT_DISPLAY) {
        Log.w(TAG, "Non-default displayId=$displayId detected, using DEFAULT_DISPLAY")
        null  // Fall back to default
    } else {
        displayId
    }
}
```

Or simpler — just remove the `setDisplayId()` call entirely since the emulator/single-display case doesn't need it:

```kotlin
private fun buildGesture(stroke: StrokeDescription): GestureDescription {
    return GestureDescription.Builder().addStroke(stroke).build()
    // TODO: re-introduce setDisplayId() after proper multi-display testing
}
```

For SimpleSmsSend recurring failures:

- Consider adding a "try different approach after 3 failed identical actions" policy

For BrowserMultiply:

- This is likely a model capability issue, not a prompt issue
